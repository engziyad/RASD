# SIEM Deployment Notes

The generated queries in [`queries/`](../queries/) return what the tested rules return on every test event when `rasd parity` runs them through its interpreters of KQL and SPL; they have not yet run in a live SIEM. What parity cannot know is how your environment names tables and fields; that lives in one file, [`tools/mappings.yml`](../tools/mappings.yml).

## Microsoft Sentinel / Defender (KQL)
- Process, process-access and registry rules read a function named `Sysmon` (the common community parser). If your parser has another name, change the `kql.logsources` entries in `mappings.yml`.
- Security events come from `SecurityEvent`, System events from `Event | where EventLog == "System"`. The provider field is mapped from Sigma's `Provider_Name` to `Source`.
- The stock `Event` table has no `ServiceName` or `ImagePath` column, and `TicketEncryptionType` is not a `SecurityEvent` column in every workspace. For these two tables the converter extends every field a rule reads (except the native columns listed under `kql.eventdata` in `mappings.yml`) from the `EventData` XML before the filter:
  `| extend ImagePath = coalesce(tostring(column_ifexists("ImagePath", "")), extract(@'Name="ImagePath">([^<]*)<', 1, EventData))`.
  A real column wins when it exists; otherwise the value comes from the XML. `rasd parity` fails if a query reads such a field without extracting it. Values are XML-escaped in `EventData` (`&amp;`, `&lt;`), so a rule value containing `&` or `<` would need the escaped form.
- Linux process-creation rules read the `SysmonForLinux` parser function over the Syslog table, with the Sysmon field names (`Image`, `CommandLine`, `ParentImage`). If your Sysmon for Linux data lands elsewhere, change `kql.logsources.linux/process_creation`.
- Web rules read the stock `W3CIISLog` table. The Sigma webserver fields have hyphens (`c-ip`, `cs-uri-stem`), so `kql.fields` renames them to the table's columns (`cIP`, `csUriStem`, `scStatus` ...). For nginx or Apache logs in a custom table, change the `webserver` log source and those column names.
- Process-creation rules read Sysmon EID 1. To run them on Security 4688 instead, point `process_creation` at `SecurityEvent | where EventID == 4688` and map `Image` to `NewProcessName` and `ParentImage` to `ParentProcessName` under `kql.fields`; 4688 has no `OriginalFileName`, so renamed-binary branches go blind. To check an exported Security log against the rules first, run `rasd doctor <export> --profile windows-security-4688`.
- String columns in Kusto are never null, so negations need no special handling; regular expressions use RE2, which is why `validate.py` rejects lookarounds, backreferences, atomic groups and possessive quantifiers.
- Deploy each query as an analytics rule. Map entities (host, account, process) for the incident graph, and use the contract's `detection_logic.severity` as the rule severity.
- Correlation queries (`queries/kql/correlations/`) count exactly with `array_length(make_set())` - `dcount()` is an estimate - and bin on `window_start = bin(TimeGenerated, 600s)`. Schedule them every 10 minutes with a 20-minute lookback and group alerts on `window_start` and the group-by fields ([CORRELATIONS.md](CORRELATIONS.md#in-the-siem)).

## Microsoft Defender XDR advanced hunting (optional)
- [`queries/mde`](../queries/mde/) holds a query for every rule whose log source a Defender table carries: process creation (`DeviceProcessEvents`) and registry values set (`DeviceRegistryEvents`, `ActionType == "RegistryValueSet"`). Process access and the Windows Security and System events have no matching Defender table, and web logs are not in Defender, so those rules get no Defender query. Defender for Endpoint on Linux does write `DeviceProcessEvents`, but its path columns are not modelled here yet, so the Linux rules have no Defender query either. The parity check runs the generated query, the table's `ActionType` filter included, on every test event written the way Defender writes it, folder and file name split both ways the exports vary; it has not yet run in a Defender tenant.
- Each query starts from the Defender table, rebuilds the rule's own field names with one `extend` (`Image` from `FolderPath` and `FileName`, `User` from `AccountDomain` and `AccountName`, `TargetObject` from `RegistryKey` and `RegistryValueName` with the hive names Sysmon uses), then applies the same filter as the Sentinel query. The mapping is in the `mde` section of [`tools/mappings.yml`](../tools/mappings.yml).
- `FolderPath` is documented as the folder, but exports often hold the full path; the extend accepts both. `rasd parity` runs every query, extend included, on every test event written both ways, and on registry keys written with Defender's `HKEY_*` hive names.
- The queries keep every column, so `Timestamp`, `DeviceId` and `ReportId` reach the result, as a custom detection rule wants for alert time, device scope and the process tree.

## Splunk (SPL)
- **Splunk app:** [`queries/splunk_app`](../queries/splunk_app/README.md) is generated on every build. `rasd/` holds the indexes, a `Provider_Name` extraction from the event XML, one scheduled alert per detection (`RASD - <detection id>`, every 5 minutes over the 5-minute slice that closed 5 minutes earlier, so runs tile time and no event alerts twice; one alert per host, each also logging an event with the alerting host to `rasd_alerts`), one per correlation (once per window length over the last two windows plus 3 minutes, keeping only the most recent complete window, so each window is reported by exactly one run with the search head in UTC or a fixed-offset time zone; one alert per window and group, the group written as the alerting host) and three reports - **RASD - alert export** and its `(audit)` and `(scheduler)` fallbacks - whose CSV is the `--siem-alerts` input of `rasd evidence`. `rasd_forwarder/` holds the Universal Forwarder inputs (`renderXml = true`, so the sources match the queries). It needs the Splunk Add-on for Microsoft Windows and the Splunk Add-on for Sysmon for field extractions.
- Sysmon events: `index=sysmon source="XmlWinEventLog:Microsoft-Windows-Sysmon/Operational"`; Windows events: `index=wineventlog` with the XML sources. `EventID` is mapped to `EventCode`.
- Linux events: `index=linux sourcetype="sysmon:linux"`, with the Splunk Add-on for Sysmon for Linux extracting the Sysmon fields. Web events: `index=web sourcetype=access_combined`, whose built-in extractions give `clientip`, `method`, `uri_path`, `uri_query`, `status` and `useragent`; `spl.fields` maps the Sigma webserver fields to them.
- Every query is a raw search that starts with `index=`, so it pastes into a saved search or the REST API unchanged.
- Inside a `NOT`, fields are read as `coalesce('F', "")`: in Splunk, `NOT` over a missing field is NULL and `where` would drop the event. Parity tests this on events with each rule field removed and emptied.
- Schedule each saved search with a window that matches its latency target (see the Detection Latency weights in [QUALITY_MODEL.md](QUALITY_MODEL.md)).

## Before going live
1. `rasd doctor <export from your SIEM> --profile auto` - the [telemetry profile](../profiles/README.md) that fits the export (ECS, CIM, ASIM, Defender), fields present, command lines not truncated.
2. `rasd replay <export> --profile auto --assets assets.csv` - alert volume forecast per rule and the risk ranking; `rasd benchmark <export>` - rule cost on your data volume.
3. `rasd tune` - measure every tuning proposal before adding it; never add a filter that hides an attack variant.
4. Record each rule's deployment (SIEM, rule name, schedule) in your change system; name SIEM rules after the detection id so `rasd evidence --siem-alerts` can match their alerts.

## Objective

Do what an attacker does after reading the lures RASD-Deceive plants: try the honey account's credential (one LDAP bind as svc\_backup\_adm with a wrong password) and request a service ticket for the honey SPN account (svc\_sqlreport, as every Kerberoasting tool does for each SPN it enumerates), and prove that the domain controller's events fire the two deception rules. The password is random and never the lure's; the ticket stays in the session cache; nothing is exported or cracked.

## Prerequisites

- Domain-joined lab workstation and a lab domain controller
- The decoys deployed in the lab domain: deceive\\Deploy-RasdDecoys.ps1 -LabConfirmed -Accounts (svc\_backup\_adm with its description, adm\_helpdesk\_tier2, svc\_sqlreport with its SPN)
- DC audit policy: Account Logon &gt; Audit Kerberos Authentication Service = Failure (4771), Audit Credential Validation = Failure (4776), Audit Kerberos Service Ticket Operations = Success and Failure (4769); Logon/Logoff &gt; Audit Logon = Failure (4625)
- A lockout threshold that leaves the decoy one failure of room, or none; the step refuses otherwise

## Safety notes

- Runs only with -LabConfirmed on a machine its owner marked as a lab (red/lab/README.md, Lab guard)
- The bind refuses unless the account carries the decoy's description from deceive/decoys.yml, so a real account with the same name is never tried
- The bind uses a random 40-character password and refuses when one more failure could lock the decoy
- One ticket request; the ticket is not exported, saved or cracked, and klist purge runs first so the DC really logs it

## Execution

1. Invoke-RasdEmulation.ps1 -Test honey\_account\_use -LabConfirmed
2. The first step looks the decoy up, checks its description and badPwdCount, and binds once with a random password (System.DirectoryServices.DirectoryEntry)
3. The second step reads the honey SPN account's servicePrincipalName, purges the session's ticket cache and requests one service ticket (System.IdentityModel KerberosRequestorSecurityToken)
4. collect\_artifacts.ps1 saves klist output and the decoys' AD attributes at run time
5. Export the domain controller's Security log (Export-LabTelemetry.ps1 -LogName Security -EventId 4625,4771,4776,4768,4769) and pass it to evidence: both events are logged on the DC about this workstation

## Cleanup

- Nothing persists on disk or in the registry; the failed bind adds one badPwdCount to the decoy, which the lockout observation window resets, and the ticket lives in the session cache until it expires

**Verification:** No files or registry values are created; klist purge drops the ticket early; the decoy's badPwdCount is back to 0 after the observation window

Script: [`cleanup.ps1`](cleanup.ps1) (exit code 0 only when the host is verified clean).
